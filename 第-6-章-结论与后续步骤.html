    7. 第 6 章 - 结论与后续步骤

    7.1. 已构建的内容

    本文档已将原 2014 年文档中 [RdvMedecins] 应用的核心功能和身份验证移植到了当前的技术上：

    • 一个完整的 [NestJS] 服务器（[TypeORM] 实体、DAO、业务层、Web 层），提供与原 Spring 4 服务器相同的 11 条 JSON 业务路由，使用相同的端口（8080），现在全部受 JWT 令牌保护；
    • 一个身份验证层（[@nestjs/passport] + [@nestjs/jwt]）：登录名/密码身份验证（POST /login）、随每个后续请求出示的签名令牌，以及针对两条修改数据的路由的基于角色的访问控制（[@Roles]('ADMIN') + [RolesGuard]）；
    • 一个 [Angular] 客户端（独立组件、信号），提供与原 AngularJS 1.x 客户端相同的功能——选择医生和日期、查看日历、预约和取消预约——并补充了登录界面、持久会话（localStorage）、可根据已登录用户角色自适应的 Bootstrap 界面（USER 角色看不到预约按钮），以及在法语和英语之间切换界面的能力（[@ngx-translate/core] + [@ngx-translate/http-loader]）。

    数据库的核心没有改变（同样的医生/客户/时间段/预约表，同样的约束），只是增加了 [users] 表；总体的分层架构也没有改变——更新的只是实现它的工具。

    与原文档中身份验证机制相比有两处有意为之的差异，已在第 3 章中详细说明：使用 JWT 令牌取代随每个请求发送的 HTTP Basic 头，以及每个用户使用单个 [role] 列取代跨三张表的多对多关系。第三处差异——这一处属于功能方面——是本次移植有意做出的选择：USER 角色现在可以查看日历（只读），而在原文档中，它仅用于演示完全拒绝访问的情形。

    7.2. 尚未涉及或有待移植的内容

    除上述内容外，原文档还涵盖了另外两个主题——其中一个现已处理，另一个被有意排除在外，第三个则推迟到后续阶段：

    7.2.1. 法语/英语本地化——已在本文档中处理

    原文档使用 angular-translate 库来实现界面在法语和英语之间的切换。本次移植使用当前 [Angular] 生态系统中与之对应的 [@ngx-translate/core] 来实现这一功能（并搭配 [@ngx-translate/http-loader]，它通过 HTTP 从 public/i18n 文件夹加载 fr.json/en.json 字典）——参见第 5 章。另一种可行方案 @angular/localize 被排除了：它需要为每种语言单独编译，而 ngx-translate 允许在不重新加载页面的情况下即时切换语言——这种行为更接近原文档。

    7.2.2. 客户端的“调试”模式——被有意排除在范围之外

    原文档包含一种可从界面激活的技术显示模式，可以访问当前视图的原始模型（AngularJS 1.x 的 $scope）——这在 2014 年是一个很有用的特性，当时可用于检查 AngularJS 应用的开发工具还很有限。本次移植不再重现它：当前的 [Angular] 开发工具（[Angular] DevTools，官方浏览器扩展）如今可以在应用之外，提供比重新集成到界面中的自定义调试面板全面得多的组件、信号及其输入/输出检查。添加这样的面板，无异于重新制作一个已由生态系统提供的工具的劣质版本——因此这一决定是最终的，而不仅仅是推迟。

    7.2.3. 人为的网络延迟——推迟

    原文档允许在每次服务器响应之前设置人为延迟，以便观察界面在慢速网络下的行为（加载指示器、按钮的临时禁用等）。本次移植中尚无与之对应的功能。

    7.3. 关于本文档所用方法的说明

    本文档的编写系统地依托于实际执行过的代码：每条服务器路径都经过测试（包括身份验证场景：登录成功/失败、不带令牌访问、使用错误角色访问），每张客户端截图（第 5 章）都是通过与实际运行的应用交互获得的——一个自动控制的 Chromium 浏览器，使用所提供 SQL 脚本中的演示数据。这一方法还在编写本文档期间发现了在 [TypeORM] 中使用计算列（[@RelationId]）时的一个特定问题——该问题已在第 3 章中报告并修正，直接体现在交付的代码中。这一要求也解释了为什么本文档不包含 Postman 截图：与其模拟它们，不如把这一步留给文档作者，他可以直接在自己的工作站上创建。

    7.4. 立即可以进一步探索的内容

    在等待本次移植的后续步骤期间，随本文档提供的服务器和客户端为您自行试验提供了一个可直接使用的基础：

    • 添加新的医生或新的患者（目前只能通过修改 SQL 脚本来完成——同样受 [@Roles]('ADMIN') 保护的路由 /addDoctor 可以作为一个很好的入门练习）；
    • 添加第三种角色，或具有多个角色的用户——借此可以非常具体地评估放弃单列 [role] 这一简化方案的代价（参见第 3 章）；
    • 修改客户端的呈现（颜色、布局）而不改动服务器——这是验证客户端分层架构确如所宣称的那样运作的好办法；
    • 查看所交付服务器和客户端中每个文件夹的 README 文件：每个文件都在其上下文中解释了所含文件的作用。
