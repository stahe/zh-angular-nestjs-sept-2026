    • 第 20–24 行：[DROP TABLE IF EXISTS …] ——脚本每次执行时都从空数据库开始，按依赖关系的相反顺序删除（从引用 `[slots]` 和 `clients` 的 `appointments` 开始，一直到没有任何表引用的 `users`）：[MySQL] 会拒绝删除仍被外键引用的表；
    • 第 48 行：[doctor_id INT NOT NULL]，然后是第 53 行：[CONSTRAINT fk_slots_doctor FOREIGN KEY …] ——一个时间段总是属于某位医生；
    • 第 64 行：[CONSTRAINT unq1_appointments UNIQUE (day, slot_id)] ——应用的核心业务规则：同一天的同一个时间段只能被预约一次。防止重复预约的正是这个约束，而且只有这个约束——验证器和业务层都不会显式地再次检查它（见下文 addAppointment）；
    • 第 67–74 行：[CREATE TABLE users (…)] ——本步骤新增的表。`login` 是 UNIQUE 的（两个用户不能共用同一个登录名）；`password` 存放使用 bcrypt 哈希后的 密码（绝不存明文）；role 为 'ADMIN' 或 'USER'——一个简单的文本列，而原始文档使用三张表（users、roles、users_roles）以允许每个用户拥有多个角色。由于本应用只需要两个互斥的角色，原来的多对多关系就显得过度了；
    • 第 91–93 行：[INSERT INTO users …] ——两个演示账户，admin/admin（角色 ADMIN）和 user/user（角色 USER），其密码已用 bcrypt 哈希（10 轮加盐）——绝不存明文，在这个演示脚本中也是如此。

      import { [PrimaryGeneratedColumn], [VersionColumn] } from 'typeorm';

  export abstract class AbstractEntity {
    @PrimaryGeneratedColumn()
    id: number;

    @VersionColumn()
    version: number;
  }

    我们来评注这段代码：

    • 第 4 行：[@PrimaryGeneratedColumn()] ——通过 DBMS 声明一个自增主键——完全等同于 JPA 中的 @Id + @GeneratedValue(strategy = GenerationType.AUTO)；
    • 第 7 行：[@VersionColumn()] ——[TypeORM] 原生的 乐观锁机制：[TypeORM] 在每次修改时自动递增该列，如果您试图保存一个版本与数据库中不一致的实体（说明其间有人修改过它），就会抛出错误——完全等同于 JPA/Hibernate 中的 @Version；
    • 第 3 行：[export abstract class AbstractEntity {] ——这个类 没有 被 [@Entity] 装饰：它本身不对应任何表。[TypeORM] 将这种技术称为“具体表继承”：每个被 [@Entity] 装饰的子类都有自己的表，包含所有继承的列——完全等同于 JPA 中的 @MappedSuperclass。

      import { [Column], [Entity], [JoinColumn], [ManyToOne], [RelationId] } from 'typeorm';
  import { AbstractEntity } from './abstract.entity';
  import { Doctor } from './doctor.entity';

  @Entity({ name: 'slots' })
  export class Slot extends AbstractEntity {
    @Column({ name: 'start_hour' }) startHour: number;
    @Column({ name: 'start_minute' }) startMinute: number;
    @Column({ name: 'end_hour' }) endHour: number;
   @Column({ name: 'end_minute' }) endMinute: number;

   @ManyToOne(() => Doctor, (doctor) => doctor.slots)
   @JoinColumn({ name: 'doctor_id' })
   doctor: Doctor;

   @RelationId((slot: Slot) => slot.doctor)
   doctorId: number;
 }

    我们来剖析这段代码：

    • 第 7–10 行：[@Column({ name: 'start_hour' }) startHour: number; …] — 预约时间段的四个时间边界（开始和结束的小时/分钟），四个单独的整数，每个都被显式映射到其 snake_case 列（start_hour、start_minute、end_hour、end_minute）；
    • 第 12 行：[@ManyToOne(() => Doctor, (doctor) => doctor.slots)] ——多个时间段属于同一位医生。默认情况下，[TypeORM] 在读取时间段时 不会 加载“doctor”关系（默认的“懒”行为）：您必须显式请求它（在查询中使用 relations 选项：[...]）——正如在 JPA 一侧，FetchType.LAZY 要求在 JPQL 查询中显式使用 `left join fetch` 才能获取医生一样；
    • 第 13 行：[@JoinColumn({ name: 'doctor_id' })] ——指定表 [slots] 中外键列的名称；
    • 第 16 行：[@RelationId((slot: Slot) => slot.doctor)] ——在 [TypeORM] 一侧，完全对应且符合惯用法地替代了原始项目中的只读字段 idMedecin（[@Column](name = "id_medecin", insertable = false, updatable = false)）：它直接公开外键的值，而无需加载整个 [Doctor] 实体——这对于构建轻量级的 JSON 响应很有用（见下文 Web 层）。

    注意：[@RelationId] 字段是一个 虚拟列，由 [TypeORM] 事后计算——它不是真正的 SQL 列，不能用在“查询构建器”的 WHERE 子句中（见下文 [SlotRepository]）。它仅用于在实体加载之后 获取 外键的值。

  import { AbstractEntity } from './abstract.entity';
  import { Client } from './client.entity';
  import { Slot } from './slot.entity';

  @Entity({ name: 'appointments' })
  @Unique('unq1_appointments', ['day', 'slot'])
  export class Appointment extends AbstractEntity {
    @Column({ type: 'date' })
   day: string;

   @ManyToOne(() => Client)
   @JoinColumn({ name: 'client_id' })
   client: Client;

   @ManyToOne(() => Slot)
   @JoinColumn({ name: 'slot_id' })
   slot: Slot;

    我们来评注这段代码：

    • 第 7 行：[@Unique('unq1_appointments', ['day', 'slot'])] ——在 [TypeORM] 一侧引用数据库脚本中的 SQL 约束。注意：这里引用的是 关系 的名称（“slot”），而不是 [@RelationId] 字段（“slotId”）——后者是虚拟列，[TypeORM] 不接受它出现在 @Unique 约束中。[TypeORM] 自己会把 'slot' 映射到其实际的外键列（slot_id）；
    • 第 9 行：[@Column({ type: 'date' })] ——类型为 'date'（而不是 'datetime'）：只保留日期，不保留时间——完全如同 JPA 一侧指定的 TemporalType.DATE；

    4.5. DAO 层（src/repositories/）

    DAO 层（数据访问对象）是项目中唯一直接与 TypeORM/MySQL 通信的部分——相当于原始项目中的 Spring Data 接口（包 rdvmedecins.repositories）。

    理解 Spring Data 与 [TypeORM] 之间最重要的区别：使用 Spring Data 时，您只需 声明一个接口 （extends CrudRepository<...>）就能自动获得基本方法（findAll、findOne、save、delete……）——Spring 自己会在启动时生成实现它的类。而使用 [TypeORM] 时，不会根据接口自动生成实现：我们直接注入 [TypeORM] 提供的泛型 Repository<Entity>（通过 [@InjectRepository]），然后自己编写想要公开的方法，或基于该 Repository 预定义的方法，或使用 查询构建器 来完成更特定的查询。

    4.8. 身份验证（src/auth/）

    本节记录在课程这一阶段新增的基于令牌的身份验证（JWT）和基于角色的访问控制（ADMIN/USER）——它在功能上等同于原始文档中的 Spring Security 层，使用 [NestJS] 生态系统的标准工具重写：[@nestjs/passport] 和 @nestjs/jwt。

    与原始项目的两处有意差异，在此一次性说明：

    1. 使用 JWT 而不是 HTTP Basic。原始的 Spring 项目在每个请求中都发送 Authorization: Basic <login:password in Base64> 头：因此密码（经过编码，而非加密）在每次调用时都会通过网络传输。此次移植改用令牌：JWT （JSON Web Token）。密码仅在登录时提交一次（POST /login）；服务器随后返回一个签名令牌，客户端在之后的每个请求中都携带该令牌（Authorization: Bearer <token> 头）。这是此类 API 当前的通行做法，正如上一章的结论中已经提到的那样。
    2. 每个用户一个角色，仅占数据库中的一列，而不是原始项目中的多对多关系（users/roles/users_roles）——见上文的 user.entity.ts。

    在阅读后面的代码之前需要理解的一个架构要点：当守卫拒绝一个请求（401 Unauthorized、403 Forbidden）时，响应绝不会经过常规的 [ServerResponse]<T> 封装（{ status, data }）：[NestJS] 直接以其原生 JSON 格式响应，即 { statusCode, message, error }。这是一个深思熟虑的选择：安全错误由守卫在进入控制器之前处理，而 [ServerResponse]<T> 则是由控制器针对业务错误（资源未找到、日期无效等）生成的。因此，[Angular] 客户端必须区分这两种类型的错误响应（见下一章的 auth.interceptor.ts）。

    constructor(private readonly reflector: Reflector) {}

   canActivate(context: ExecutionContext): boolean {
     const requiredRoles = this.reflector.getAllAndOverride<Role[]>(ROLES_KEY, [
       context.getHandler(),
       context.getClass(),

  import * as bcrypt from 'bcryptjs';
  import { UserRepository } from '../repositories/user.repository';

  import { JwtPayload } from './jwt.strategy';

  @Injectable()
 export class AuthService {
   constructor(
     private readonly userRepository: UserRepository,
     private readonly jwtService: JwtService,
   ) {}

   async validateUser(login: string, password: string): Promise<User | null> {
     const user = await this.userRepository.findByLogin(login);
     if (user === null) {
       return null;
     }
     const passwordCorrect = await bcrypt.compare(password, user.password);
     return passwordCorrect ? user : null;
   }

   login(user: User): LoginResult {
     const payload: JwtPayload = { sub: user.id, login: user.login, role: user.role };
     return {
       accessToken: this.jwtService.sign(payload),
       login: user.login,
       name: user.name,
       role: user.role,
     };
   }
 }

    我们来解释这段代码：

    • 第 10 行：[export class AuthService {] ——在概念上相当于原始 Spring Security 项目中的 AppUserDetailsService 类，这里再加上了令牌的生成；
    • 第 16 行：[async validateUser(login: string, password: string): Promise<User | null> {] ——验证存在具有此登录名的用户，并且所提供的密码与之匹配；如果一切正确则返回该用户，否则返回 null；
    • 第 21 行：[const passwordCorrect = await bcrypt.compare(password, user.password);] ——bcrypt.compare() 使用与 user.[password] 中存储的相同的盐值对密码进行哈希，然后比较两个结果——存储的密码从不会被解密（哈希是不可逆的）；

    • 第 16 行：[“strictNullChecks”: true,] ——要求显式处理 null/undefined 值（使用 ?、??、if 语句……）——这是 TypeScript 严格模式中的选项之一，这里单独启用，而不是启用完整的严格模式（第 17 行：noImplicitAny 仍设置为 false，限制更宽松）：这是出于教学考虑的折中，既保留类型安全的精髓，又不要求为每个变量都添加类型注解。
